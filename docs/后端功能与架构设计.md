## OpenBlog 后端功能清单与架构设计（参考文档）
> 文档目标：在你后续实现代码时，所有业务逻辑、数据结构、接口边界、鉴权策略、可扩展点都优先以本文件为准。
>
> 当前项目仅有 Spring Boot 骨架（web 依赖），本文件先给出“可落地”的后端设计蓝图；你后续实现时再逐步引入依赖（JPA/Redis/JWT/文件存储等）并完成映射。

---

## 0. 产品与技术假设
### 0.1 产品形态（面向博客平台）
1. 公开访问：未登录用户可浏览文章列表、文章详情、分类/标签页、搜索（可选）。
2. 账号体系：登录后可发布/编辑文章、对文章进行点赞收藏（可选）、评论、关注（可选）。
3. 内容管理：作者发布/管理文章（本阶段不包含管理员审核流程）。
4. 数据完整性：支持草稿、发布、下架/软删除；编辑历史/版本回滚本阶段不做（预留后续扩展）。

### 0.2 技术栈建议（后续逐步引入）
1. Java 17 + Spring Boot 3.5.x
2. Web：Spring MVC（当前依赖 `spring-boot-starter-web`）
3. 持久化：JPA（或 MyBatis；建议 JPA 以加快开发）
4. 数据库：MySQL 8（本项目按 MySQL 落地）
5. 鉴权：JWT（Access Token + Refresh Token）+ 角色权限（RBAC）
6. 缓存：Redis（可选，建议用于热点文章列表、会话刷新令牌、限流）
7. 搜索：MVP 不引入 ES；可先用数据库 LIKE（或直接不做搜索接口）
8. 文件存储：本地存储为默认实现（MVP）；可抽象接口以便后续切换到对象存储
9. 可观测性：Actuator + 结构化日志（建议）

> 若你希望“最小可运行版本（MVP）”先落地，建议顺序：JPA + JWT + 文章/评论/用户的最小表结构 + 基础接口。

## 1. 后端功能清单（按业务模块拆分）
下面按“最终要支持的能力”列出清单，并在每个能力后给出建议的接口、数据结构要点与权限要求。

### 1.1 用户与账号体系
1. 注册与登录
   - 支持：邮箱/用户名（建议邮箱唯一）登录与注册（可选短信/第三方登录，后续再加）
   - 支持：用户名/邮箱校验、密码哈希（BCrypt/Argon2 建议）
   - 后续可选：注册验证码、账号激活、密码重置
2. 账号资料
   - 头像、昵称、个人简介、主页 URL、注册时间
   - 资料更新权限：本人；管理员可进行额外管理
3. 角色与权限（RBAC）
   - 系统角色：`ADMIN`、`AUTHOR`（或 `EDITOR`）、`READER`
   - 权限粒度建议：将“功能点”抽象为 `Permission`（例如 `article:create`、`article:publish`、`admin:user:ban` 等）
4. 用户状态与风控
   - 禁用/封禁：禁止登录、禁止发评论、禁止发布（取决于封禁类型）
   - 限流：对登录、评论接口限流，防刷
5. 关注/粉丝（纳入 MVP）
   - 关注用户、查看某用户的文章列表
   - 权限：用户可关注/取消关注；浏览公开

#### 建议 API（示例）
- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/refresh`
- `GET /api/v1/users/me`
- `PUT /api/v1/users/me`
- `GET /api/v1/users/{userId}`
- `POST /api/v1/follows/{userId}`
- `DELETE /api/v1/follows/{userId}`

---

### 1.2 文章（核心）
1. 文章基础能力
   - 文章创建：作者创建草稿
   - 文章编辑：支持更新标题、摘要、正文、封面图、分类、标签、SEO 信息
   - 文章发布：作者可直接把草稿发布为公开文章
   - 文章下架：发布后可下架（对外不可见）
   - 软删除：支持作者删除但保留历史（建议）
2. 文章状态机（建议）
   - `DRAFT`：草稿（作者私有）
   - `PUBLISHED`：已发布（对外可见）
   - `DELETED`：软删除
3. 文章内容形态
   - 正文：MVP 统一返回 `markdown`（不返回 `html`）
   - 展示：由前端自行渲染（建议使用可信的 Markdown 渲染库并做必要的内容校验/消毒）
   - 代码块、图片：支持文章内图片引用（上传/外链）
4. 文章列表与筛选
   - 分页：`page`/`size` 或 Cursor Pagination
   - 排序：时间倒序、热度、置顶（置顶优先）
   - 筛选：分类、标签、作者、状态
   - 搜索：标题/摘要关键字（可选）
5. 文章互动（纳入 MVP）
   - 点赞：对文章点赞/取消
   - 收藏：对文章收藏/取消
   - 阅读数：访问计数（注意并发与缓存策略）
7. 置顶与推荐（可选）
   - 置顶：按置顶开始/结束时间与优先级展示
   - 推荐：按规则将文章置于首页推荐位

#### 文章建议 API（最小集）
公共浏览（游客）：
- `GET /api/v1/articles`（列表，筛选+分页）
- `GET /api/v1/articles/{articleId}`（详情，只返回 `PUBLISHED`；非 `PUBLISHED` 文章视为不存在，返回 404）
- `GET /api/v1/categories/{categoryId}/articles`（可选：若不做则由列表接口完成）
- `GET /api/v1/tags/{tagId}/articles`（同上）

作者/管理员（登录后）：
- `POST /api/v1/articles`（创建草稿）
- `PUT /api/v1/articles/{articleId}`（编辑）
- `POST /api/v1/articles/{articleId}/publish`（发布：`DRAFT` -> `PUBLISHED`）
- `POST /api/v1/articles/{articleId}/unpublish`（下架/归档）
- `DELETE /api/v1/articles/{articleId}`（软删除）
- `GET /api/v1/users/me/articles`（作者自己的列表）

互动（纳入 MVP）：
- `POST /api/v1/articles/{articleId}/likes`
- `DELETE /api/v1/articles/{articleId}/likes`
- `POST /api/v1/articles/{articleId}/favorites`
- `DELETE /api/v1/articles/{articleId}/favorites`

---

### 1.3 分类与标签（内容组织）
1. 分类（Category）
   - 层级：仅一级分类（建议先简单）
   - 字段：名称、slug（URL 映射）、排序、启用状态
   - 权限：管理员可增删改；作者可选择分类（若不想管理也可先让作者自定义分类但会导致脏数据）
2. 标签（Tag）
   - 建议：标签为自由组合但需要限制
   - 字段：名称、slug、引用次数（可选）、热度（可选）
   - 管理：管理员可统一维护；作者可推荐标签（需要校验/创建策略）

#### 建议 API
- `GET /api/v1/categories`
- `GET /api/v1/tags`
- `POST /api/v1/admin/categories`（管理员）
- `PUT /api/v1/admin/categories/{id}`
- `POST /api/v1/admin/tags`
- `PUT /api/v1/admin/tags/{id}`

---

### 1.4 评论系统（互动核心）
1. 评论基础能力
   - 对文章评论（一级评论）
   - 回复评论（多级回复，MVP 支持；最大回复深度 5 级以防滥用）
   - 禁用用户后：禁止发评论、可隐藏其评论
2. 评论状态
   - `APPROVED`：已审核通过
   - `DELETED`：软删除/隐藏
3. 富文本与安全
   - 评论内容建议纯文本或经过 HTML 清理
   - 防 XSS、SQL 注入天然靠参数化
4. 互动（可选）
   - 评论点赞
5. 通知（可选）
   - 当对方收到回复：发送站内通知/邮件

#### 建议 API
- `GET /api/v1/articles/{articleId}/comments?page=0&size=20`（个人模式：仅对已登录用户开放）
- `POST /api/v1/articles/{articleId}/comments`
- `POST /api/v1/comments/{commentId}/replies`（允许多级回复；或统一在创建评论接口里使用 `parentId`）
- `DELETE /api/v1/comments/{commentId}`（作者/管理员软删除）

> 回复深度规则（MVP 约束）：
> - `parentId` 为顶级评论时视为第 1 级
> - 当将要创建的新回复深度 > 5 时直接返回业务错误（例如 `400x`）

### 1.6 媒体与文件上传（封面图/文章内图片）
1. 上传能力
   - 封面图上传（作者）
   - 文章内图片上传（作者，可返回图片 URL）
2. 存储抽象
   - 统一的 `StorageService`：
     - 本地存储实现（开发阶段）
     - 未来替换为对象存储实现（S3/OSS/COS）
3. 安全与限制
   - 校验文件大小、后缀、内容类型
   - 防止恶意脚本（图片通常可通过内容类型和扩展验证并做白名单）
4. 链接访问
   - 返回可访问 URL（若走对象存储可直接 CDN）

#### 建议 API
- `POST /api/v1/media/upload`（返回 `{url, thumbUrl, key, width, height}` 等）
- `GET /api/v1/media/{key}/thumb`（缩略图接口：返回 `{thumbUrl, width, height}`；可带 `width/height` 参数）
- `DELETE /api/v1/media/{key}`（可选）

媒体缩略图策略（MVP 约束）：
- 默认生成固定长边（例如 320px），等比压缩（具体尺寸可后续调整，但字段与接口保持不变）

2. 推荐

3. 分页与排序一致性

## 2. 后端总体架构设计（模块化 + 分层 + 可扩展）
### 2.1 分层目标
1. 控制器（Controller）：只负责参数校验、调用用例、返回结果
2. 应用层（Application/Service）：实现“用例/业务流程”，控制事务边界
3. 领域层（Domain）：实体、值对象、领域服务（可选；轻量即可）
4. 基础设施层（Infrastructure）：JPA Repository、JWT、Redis、文件存储、外部服务适配
5. 表现层契约（DTO/VO）：统一请求/响应结构，避免暴露内部实体

> 若你后续更偏 DDD，也可以将 Application 层按“UseCase”组织，比如 `CreateArticleUseCase` 等。

### 2.2 模块划分（建议包结构）
建议你按领域模块组织代码（即使目前只有 skeleton 也建议现在就定结构，后续更容易维护）：
- `com.yqz.openblog.common`：通用能力（返回码、异常、校验、分页、审计日志）
- `com.yqz.openblog.security`：JWT/认证/授权/当前用户解析
- `com.yqz.openblog.user`：用户、角色、权限
- `com.yqz.openblog.article`：文章、统计、交互（点赞/收藏可放此模块）
- `com.yqz.openblog.comment`：评论
- `com.yqz.openblog.tag`：分类与标签
- `com.yqz.openblog.media`：上传与存储
- `com.yqz.openblog.admin`：管理接口（也可拆到各模块里按权限复用）

## 3. 关键技术点设计（必须先定，后续避免返工）
### 3.1 统一返回结构与错误码
1. 统一响应：所有接口返回同一结构（即使成功/失败）
2. 建议响应体：
   - `code`：业务码（0 表示成功，非 0 表示失败）
   - `message`：人类可读
   - `data`：业务数据（可为空）
   - `traceId`：可选，用于排障
3. 建议错误码分类
   - 通用参数错误（400x）
   - 鉴权失败（401）
   - 权限不足（403）
   - 资源不存在（404）
   - 业务冲突（409，例如重复发布）
   - 服务器异常（500）
4. 建议使用 `@RestControllerAdvice` 统一异常处理

---

### 3.2 参数校验与 DTO 设计
1. 请求 DTO 使用 Bean Validation（`jakarta.validation`）
2. 必填字段、长度限制、枚举校验、跨字段校验要明确
3. 分页参数统一封装（建议支持 `page`/`size` 与最大 size 限制）

---

### 3.3 鉴权与权限（JWT + RBAC）
1. 认证
   - 登录成功返回 `accessToken` 和 `refreshToken`
   - `accessToken`：短有效期（例如 15min）
   - `refreshToken`：长有效期（例如 30d）
2. 授权
   - Token 中携带 `roles` 或 `permissions`（建议只携带 roles，permissions 由后端加载/映射；取决于你后续复杂度）
   - 使用方法级别注解或拦截器检查权限
3. 安全细节
   - 密码永不明文存储：BCrypt/Argon2
   - 防止刷新令牌被滥用：刷新时旋转 refresh token（推荐）
   - 封禁用户：拦截登录与鉴权请求
4. 当前用户上下文
   - 通过 `SecurityContext` 或自定义 `CurrentUser` 解析 userId

---

### 3.4 数据一致性与事务边界
1. 典型场景
   - 发布文章：更新状态 + 写入统计（若有）+ 触发消息/通知
   - 点赞：幂等（重复点赞不重复计数）
2. 建议事务边界
   - Application 层中一个用例一个事务（除非引入复杂事件最终一致性）
3. 乐观锁（本阶段不做；避免引入额外字段与返工）

---

### 3.5 并发与性能
1. 阅读数
   - 纯数据库增计数在高并发下会成为瓶颈
   - 建议：先写 Redis 计数（或异步队列）再定时落库
2. 热门排序
   - 热度指标可缓存
3. N+1 查询
   - DTO 投影查询，避免实体全量加载

---

## 4. 数据模型设计（建议表结构草案）
下面给出核心实体与建议字段。具体字段命名你可以按项目风格微调，但“字段含义”和“关系”尽量保持一致。

### 4.1 用户表 `users`
- `id`：PK
- `username`：唯一（可选邮箱登录则不一定唯一）
- `email`：唯一（强烈建议唯一）
- `password_hash`：密码哈希
- `nickname`
- `avatar_url`
- `bio`
- `status`：`ACTIVE` / `BANNED`
- `role` 或（拆表）`user_role`
- `created_at` / `updated_at`

### 4.2 角色与权限（RBAC）
1. `roles`：`id`、`name`（ADMIN/AUTHOR）
2. `permissions`：`id`、`name`（article:publish 等）
3. `role_permissions`：多对多
4. `user_roles`：多对多（一般系统默认只有一个角色）

> MVP 可简化为用户表直接存 `role` 字段；升级时再迁移到 RBAC 多表。

---

### 4.3 文章表 `articles`
- `id`
- `title`
- `slug`：URL slug（可选）
- `summary`：摘要
- `content_markdown`
- `content_html`：可选（如后端渲染后保存；或仅用于缓存）
- `cover_url`
- `category_id`（可选：若文章允许无分类）
- `status`：`DRAFT`/`PUBLISHED`/`DELETED`
- `published_at`
- `author_id`（FK -> users）
- `is_pinned`（可选）
- `pinned_until`（可选）
- `view_count`（可选：先落库）
- `like_count`（可选：先落库）
- `comment_count`（可选：先落库）
- `created_at` / `updated_at`

### 4.4 文章-标签关系 `article_tags`
- `article_id`
- `tag_id`

### 4.5 评论表 `comments`
- `id`
- `article_id`
- `user_id`
- `parent_id`：顶级评论为 `NULL`
- `content`
- `status`：`APPROVED`/`DELETED`
- `like_count`（可选）
- `created_at` / `updated_at`

### 4.6 点赞表 `article_likes`
- `article_id`
- `user_id`
- 唯一约束 `(article_id, user_id)` 以保证幂等

### 4.7 收藏表 `article_favorites`
- `article_id`
- `user_id`
- 唯一约束

---

### 4.8 关注表 `user_follows`（纳入 MVP）
- `id`
- `follower_id`：关注者（userId）
- `followee_id`：被关注者（userId）
- `created_at`
- 唯一约束 `(follower_id, followee_id)` 防止重复关注

### 4.9 分类与标签
1. `categories`
   - `id`
   - `name`
   - `slug`（唯一）
   - `sort_order`
   - `status`：`ACTIVE` / `DISABLED`
   - `created_at` / `updated_at`
2. `tags`
   - `id`
   - `name`
   - `slug`（唯一）
   - `sort_order`（可选）
   - `status`
   - `created_at` / `updated_at`

---

### 4.10 媒体表 `media`
（用于封面图、文章内图片的索引）
- `id`
- `storage_type`：`LOCAL`（MVP）
- `storage_key`：对象 key
- `url`
- `thumb_url`：缩略图地址
- `size`
- `content_type`
- `width` / `height`（可选）
- `thumb_width` / `thumb_height`（可选）

### 4.11 审计日志表（建议有）
1. `audit_logs`
   - `id`
   - `operator_id`（管理员/系统）
   - `action`：例如 `article.publish`、`user.ban`
   - `target_type`：例如 `article`
   - `target_id`
   - `before` / `after`（可选 JSON）
   - `created_at`

## 5. REST API 设计规范
### 5.1 版本号与路由
1. 所有 API 建议统一加版本号：`/api/v1`
2. 管理接口建议使用：`/api/v1/admin/...`
3. 资源路径建议语义化：
   - `articles`
   - `comments`
   - `categories`
   - `tags`
   - `media`

### 5.2 分页规范
1. 推荐参数：
   - `page`（从 0 或 1 由你定，需一致）
   - `size`（建议限制最大值，如 50）
2. 返回结构建议包含：
   - `items`
   - `page`
   - `size`
   - `total`（若后续用 Cursor 可以扩展）

### 5.3 返回字段建议
1. 浏览列表：只返回列表所需字段（避免返回全文 content）
2. 详情接口：返回更多字段（包括 content）
3. 统计字段：返回 `likeCount/viewCount/commentCount`

## 6. 业务用例（Use Case）定义（落地导向）
下面用“用例”的方式描述核心流程，便于你后续实现时知道应该写哪些 Service 方法。

### 6.1 注册与登录用例
1. `RegisterUseCase`
   - 校验邮箱/用户名未被占用
   - 校验密码强度（可选）
   - 写入用户表
2. `LoginUseCase`
   - 校验凭据
   - 校验用户状态（未封禁）
   - 生成 access/refresh token
3. `RefreshTokenUseCase`
   - 校验 refresh token 有效且未被撤销
   - 旋转 refresh token

### 6.2 创建文章用例
1. `CreateArticleUseCase`
   - 校验标题/摘要长度
   - 默认状态 `DRAFT`
   - 保存文章内容（markdown）
   - 文章标签：若标签不存在可策略创建（或仅允许选择已有标签）

### 6.3 编辑文章用例
1. `UpdateArticleUseCase`
   - 校验作者权限（仅作者或管理员）
   - 更新文章字段
   - 标签增删同步（清空后重建 join 表或做差分，建议先清空重建简单实现）

### 6.4 发布文章用例
1. `PublishArticleUseCase`（直接发布；纳入 MVP）
   - 前置校验：文章必须至少有标题和正文、分类/标签可选
   - 将状态从 `DRAFT` 变为 `PUBLISHED`
   - 记录 `published_at`

### 6.5 评论创建用例
1. `CreateCommentUseCase`
   - 校验文章存在且对外可见（或内部权限）
   - 校验父评论归属文章
   - 保存评论，默认 `APPROVED`
   - 更新文章 `comment_count`（同步或异步）

## 7. 可扩展点与替换策略
### 7.1 存储替换
1. 文件存储从本地切换到对象存储时，只需替换 `StorageService` 实现
2. 数据访问从 JPA 切到 MyBatis 时，只需替换 Repository 层

### 7.2 内容渲染策略替换
1. 文章正文渲染可以：
   - 写入 `content_html`（存储换取读取性能）
   - 或读取时实时渲染（更灵活但性能压力更大）
2. 建议：先做最简单可运行策略，然后再优化。

### 7.3 搜索替换
1. MVP 不引入 ES：不做全文搜索或仅用数据库 LIKE/索引
2. 若后续确需全文搜索，再引入 ES，并替换 `ArticleSearchService` 实现即可

## 9. 最小可运行版本（MVP）建议实现顺序
为了避免你后续实现时“先写一堆但无法验证”，建议按以下顺序落地：
1. 基础工程补齐
   - JPA + 数据库连接
   - 统一返回结构 + 全局异常处理
   - 统一分页 DTO
2. 认证体系 MVP
   - 注册/登录/刷新 token
   - JWT 拦截器与当前用户解析
3. 文章 MVP（无审核；纳入 MVP）
   - 文章表 + 创建草稿 + 作者直接发布（进入 `PUBLISHED`）
   - 对外可见逻辑：只展示 `PUBLISHED`；非 `PUBLISHED` 文章通过详情接口返回 404（作者仅通过编辑/发布接口维护内容，不提供详情查看）
4. 评论 MVP（含多级回复）
   - 评论表 + 支持多级回复创建（用 `parentId` 或“回复接口”实现）
   - 列表拉取：按文章分页，并支持前端构建层级展示（树形或扁平带 parentId）
5. 分类/标签 MVP（可选）
   - 分类表 + 标签表（如果文章创建需要分类/标签）
6. 后续再做点赞/收藏/通知/媒体高级能力
