# OpenBlog 压测设计：接口上限、鉴权负担与优化支撑

> 日期：2026-08-30
> 目的：为 OpenBlog 设计一套压测方案，回答三个问题：各接口吞吐/延迟上限在哪、网关与鉴权环节的耗时负担占比多少、瓶颈在哪里，为后续优化提供可对比的基线数据。

---

## 1. 背景与目标

### 1.1 为什么压

- 当前服务的性能上限是"估计"而非"数据"，缺少基线，优化无的放矢。
- 网关（8090）与鉴权链路引入的耗时负担没有量化，无法判断"安全成本"是否值得。
- 需要一个可重复执行的压测流程，优化前测一次、优化后再测一次，用数据验证收益。

### 1.2 三个问题

| 问题 | 产出 |
|------|------|
| 接口上限 | 每个核心接口的 QPS 上限、平均 RT、P95/P99、错误率 |
| 鉴权/网关负担 | 网关转发、JWT 校验、Spring Security 授权各自占耗时多少、占比多少 |
| 瓶颈定位 | 是 DB / Redis / 线程池 / 连接池 / 网关哪一层先顶不住 |

### 1.3 被测拓扑

```
压测机（内网，勿与被测服务同机）
  │
  ▼
Nginx（18088→80）
  ├─ 静态 / SEO 路径（绕过网关）
  └─ /api/** ──► Gateway:8090（WebFlux，traceId + JWT 粗校验 + 限流）
                    └─► business:8082（Spring Security 授权 + 业务）
                            └─► message:8083（Dubbo，阿里云 DirectMail，仅验证码/通知）
```

基础设施（局域网 10.21.76.221）：MySQL 8 / Redis / Nacos / RocketMQ（均非压测对象，但观察它们是被测链路的一部分）。

## 2. 核心接口清单

按读写与缓存命中情况分组，各组至少压一个代表接口：

| 分组 | 代表接口 | 特性 |
|------|----------|------|
| 读·列表（缓存） | 文章列表分页 `/api/v1/articles` | 命中 Redis 列表缓存（版本号 key） |
| 读·详情（缓存） | 文章详情 `/api/v1/articles/{id}` | 正文缓存 + 计数每次查库合并 |
| 读·评论列表 | 评论列表 | 白名单路径，无鉴权 |
| 写·评论 | 发表评论 `/api/v1/comments` | 幂等框架（`@RepeatExecuteLimit`），鉴权路径 |
| 写·认证 | 登录 `/api/v1/auth/login` | JWT 签发，鉴权链路重点 |
| 写·验证码 | 发送验证码 `/api/v1/auth/email-code` | 触发外部邮件（Dubbo→阿里云），单独小并发 |
| 读·站点 | 站点统计 `/api/v1/site/stats`、访问计数 `/api/v1/site/visit` | 计数去重（Lua 滑动窗口） |

> 验证码接口触发真实阿里云发信（有配额、耗时 >1s），不作为常规压测对象，单独小并发或 mock 掉 message 后压 business 侧。

## 3. 工具选型

| 工具 | 定位 | 说明 |
|------|------|------|
| Apifox | 起步、日常验证 | 接口定义现成，内置性能测试基于已有用例跑，适合冒烟与小规模基准 |
| JMeter | 正式基准 | 并发梯度、自定义断言、分布式压测、监控插件更专业，最终基准用 |

量级判断：个人博客规模，Apifox 起步足够；要沉淀可复用、可复现的正式脚本再上 JMeter。

**约束**：压测机与业务服务分机；优先在局域网内压（贴近真实网络）；压测前先调高或临时关闭网关限流（见 5.1）。

## 4. 关键实验设计

### 4.1 鉴权/网关负担拆解（核心）

用"同一接口、逐层开关"拆出每层耗时。前提：接口有白名单版本与需鉴权版本可对照（或临时加一条白名单路由）。

| 实验 | 路径 | 差值含义 |
|------|------|----------|
| ① 基线 | 直连 business:8082 的白名单路径 | 纯业务耗时 |
| ② 网关基础 | 走网关:8090 的白名单路径 | ②−① = 网关转发 + traceId + 路由开销 |
| ③ 鉴权链路 | 走网关的需鉴权路径 + 有效 token | ③−② = JWT 校验 + Spring Security 授权开销 |
| ④ 鉴权失败 | 走网关 + 伪造/过期 token | 快速 401 路径耗时（防御性验证） |
| ⑤ 缓存对比 | 同一读接口：缓存命中 / 未命中 / Redis 宕机 | 缓存收益与降级代价 |

**结论记录模板**（压完填）：

| 层 | 平均耗时 | 占总耗时比例 | 结论 |
|----|----------|--------------|------|
| 网关转发 + traceId | ? ms | ? % | 可接受 / 需优化 |
| JWT 校验 + 授权 | ? ms | ? % | 可接受 / 需优化 |
| 业务逻辑 | ? ms | ? % | 主导项，看缓存/DB |
| 缓存收益 | 命中 vs 未命中差 ? ms | — | 缓存命中率需监控 |

### 4.2 接口上限（并发梯度）

每接口：1 / 10 / 50 / 100 / 200 并发，每档跑稳定期 3 分钟，记录：

- QPS / TPS
- 平均 RT、P95、P99
- 错误率
- 观察：吞吐何时不再上涨、RT 何时陡增（那个点即上限）

典型现象：并发升到某值后吞吐平台化、RT 线性增长，说明瓶颈资源已打满。

## 5. 本项目特有的坑（压测前必须处理）

| # | 坑 | 处理 |
|---|----|------|
| 1 | **网关限流会先拦**：`RateLimitFilter` 默认敏感路径 60 次/60s，压写接口会全是 429 | 压测配置档把 `openblog.gateway.rate-limit.rules` 调大或 `enabled=false`；测完还原 |
| 2 | **幂等框架会吞并发**：同一 requestId 的重复请求被 `@RepeatExecuteLimit` 拦截（返回上次结果） | 分两类压：不同 requestId 并发（真实写）、同一 requestId 重放（验证幂等不重复） |
| 3 | **外部邮件不可控**：验证码触发 Dubbo → 阿里云，耗时 >1s、有配额 | 该接口单独小并发，或 mock message 后压 business 侧 |
| 4 | **Redis 降级路径**：Redis 宕机时读缓存走 MySQL、计数走进程内 Caffeine | 单独做"关 Redis 压一遍"，量化降级代价 |
| 5 | **默认参数是假瓶颈**：`-Xmx1024M` 下 Tomcat / 连接池默认值可能先顶 | 压前确认配置，避免测出的是默认参数而非代码问题 |

## 6. 监控采集（没有监控，压测只是看个数字）

| 层 | 采集项 | 手段 |
|----|--------|------|
| 应用 | 线程池活跃数、连接池、HTTP 吞吐、RT | Spring Boot Actuator（`/actuator/metrics`、`/health`），若未开需先补 |
| MySQL | 慢查询、连接数、QPS | `slow_query_log`、`SHOW PROCESSLIST`、`performance_schema` |
| Redis | 命中率、内存、命令耗时 | `INFO stats`、`SLOWLOG` |
| JVM | GC 停顿、堆内存 | GC 日志 + `jstat` |
| 全链路 | 每段耗时（网关→business→Dubbo→message） | 网关已透传 traceId，按日志 traceId 串段 |

> 前置建议：给 business/gateway 补 Actuator 指标与访问日志耗时字段（小改动），否则每次压测都要手动捞日志。

## 8. 落地阶段

1. **阶段一（Apifox 冒烟）**：选 7 个代表接口（见第 2 节），小并发跑通，先暴露明显慢接口。
2. **阶段二（JMeter 正式基准）**：4.1 五组对照 + 4.2 并发梯度，同时开 6 节监控。
3. **阶段三（报告 + 优化）**：出报告、定优化项、改完复测出对比数据。

## 9. 风险与注意

- 压测流量会被网关限流、幂等、外部依赖等真实组件拦截，结论必须结合"是否绕过了这些组件"来解读。
- 验证码/邮件类接口严禁高并发，避免配额与误发。
- 压测属写流量时注意幂等框架的 requestId 策略，避免污染线上数据（建议用独立压测库/数据，或压测后清理）。
- 局域网内压测结果与公网真实用户体验有差异（公网多一跳 TLS/边缘），结论标注网络环境。

---

## 10. 为后续优化与简历提供支撑

- 压测产出的量化数据（网关/鉴权开销占比、接口上限、缓存收益、降级代价）可直接支撑优化决策。
- 优化后再压一轮形成"前→后"对比，可写进简历作为性能改进证据（例：优化后 P99 从 X 降到 Y）。
