## 背景与问题

网关限流已从纯 IP 升级为「设备指纹 + IP」复合识别（`FP_IP` scope，见《设备指纹限流优化》）。但面试官问到了更深一层：

> 你有指纹做标识防刷，可指纹是**客户端随请求自报**的 header——你有没有在网关校验它的**合法性**？黑灰产**构造恶意请求**怎么办？

这个问题的答案要拆成两层，否则容易答偏：

| 层面 | 含义 | 现状 |
|------|------|------|
| ① 格式/语法合法性 | 指纹"像不像"（长度、字符集、防 header 注入） | ✅ 已有：`^[A-Za-z0-9-]{16,64}$`，非法/缺失降级纯 IP |
| ② 真实/权威合法性 | 指纹是不是**这台真机自愿算出来的**，而非脚本伪造/轮换 | ❌ 缺失：服务端不签发、不绑定、不校验归属 |

**结论先行**：问题**存在**，而且不是"没做格式校验"，而是**格式校验挡不住"格式合法的伪造与轮换"**——复合 key 在「固定 IP + 每请求换指纹」下会被**完全绕过**（见 §3），比纯 IP 更差。

## 现状盘点（代码事实）

> ⚠️ 本节是**优化前**的快照（分析时点 master 代码事实）。改造后：网关新增令牌签发/消费（第 2 层）、business 新增指纹消费 + 设备锁 + 账号×设备记录（第 3 层）——业务侧不再是"零感知"，详见文末第 2/3 层落地记录。

- **全链路唯一消费点**：网关 `RateLimitFilter.deviceFingerprint()`（`OpenBlog-gateway/.../filter/RateLimitFilter.java`，优化前）——改造后网关还消费 `X-Device-Token`、business 也消费指纹。
- 校验仅正则 `^[A-Za-z0-9-]{16,64}$`；缺失/非法 → 返回 null → `buildKey()` 降级纯 IP key（`:88-91`）。
- business/message 对指纹**零感知**：无服务端签发、无账号↔设备绑定（全仓库 grep 仅命中网关 + 前端）。
- IP 维度权威：边缘 Nginx 用 `$remote_addr` 覆写 `X-Real-IP`（`vue/nginx.conf:46`），改不了；**唯独指纹头是客户端 100% 可控**。
- 前端 `deviceFingerprint.js` 本地算 32 位 hex visitorId，`http.js:31` 每次请求当普通 header 自报。
- 受 `FP_IP` 保护的路径（`application.yaml`）：login 10/分、register 5/分、email-code 5/分、refresh 20/分、feedback 20/分。
- `RateLimitFilterTest.fpIpScope_degradesToIpOnInvalidFingerprint` 证实团队把"格式校验 + 降级"当成了终点——**这正是缺口所在**。

## 攻击路径推演（证明口子真实存在）

**攻击 A｜固定 IP + 指纹轮换（最致命，直击 FP_IP 结构）**
脚本每发一次请求就生成一个**通过正则的合法 32hex**。限流 key = `gateway:rl:{指纹X}_{IP}_{path}`：
每个请求都落进**一个全新空桶**，各计数 1 → 永不触发 → 单 IP 无限刷登录/注册/发码。
对比纯 IP 至少 10/分封顶：**引入自报指纹反而废掉了一个权威维度（IP）的防护**——攻击者能每请求换一个新"身份桶"。

**攻击 B｜固定指纹 + 旋转代理**：每 IP 一桶，指纹不跨 IP 累计——原设计已诚实声明防不住，靠账号侧兜底。

**攻击 C｜不发 / 发畸形指纹**：降级纯 IP，防逃逸成立，但不是主威胁。

**本质**：把"客户端自报值"当安全判定主键，等于把限流桶的分配权交给攻击者。格式校验挡乱填，挡不住"格式合法的伪造与轮换"。

## 设计原则

1. 指纹从"可信身份"**降级为弱信号/风险信号**，不单独作为安全判定依据。
2. 网关侧补三件事：**签发验证（不可伪造，远期）**、**行为检测（反人类使用，本期）**、**保留 IP/账号兜底**。
3. 全程保持现有 **fail-open 契约**：Redis 故障降级放行、绝不 500；无指纹降级纯 IP。
4. **不新增响应码**，复用现有 `4290`，前端拦截器零改动。

## 分层优化方案

### 第 1 层（本期落地）：指纹轮换/洪泛检测 —— 网关最小改动，直击攻击 A

每 IP 维护"窗口内出现过的**不同指纹**"集合（Redis ZSET，Lua 原子）。当一个 IP 已见 `≥ budget` 个不同指纹、又出现**全新指纹** → 判定疑似脚本轮换 → 该请求 4290（`fp` 不计入集合，集合大小恒 ≤ budget，**Redis key 有界**）。

- 合法 NAT 出口下，真用户每人**一个稳定指纹**，"不同指纹数"≈ 真实设备数且通常很小；只有脚本才在窗口内疯狂换新指纹。阈值 `budget` 做配置、留裕量即可不误伤。
- 反向可选项（本期不做）：单指纹跨 IP 数 > N → 指纹不可信，强制降级纯 IP（对冲"固定指纹 + 代理池"）。

### 第 2 层（已落地）：服务端签发匿名设备令牌 —— 把自报 header 变权威标识

前端调网关签发端点，网关用私有 key 生成 **HS256 签名设备令牌**，后续请求**验签通过才认可"设备身份"**。
客户端无密钥 → 伪造不了合法令牌 → "构造恶意请求"被挡在签发点；签发端点按 IP 限流。
> **落地语义（用户决策：deviceId 计桶、指纹仅附带）**：令牌只含每次签发随机的 deviceId（UUID），**不**承载/绑定指纹、不比对"当前指纹==签发指纹"。限流桶身份 = deviceId，指纹降级为附带的风险信号（第 1 层守卫 + 日志 + 第 3 层账号×设备绑定）。收益：换身份成本被压在 IP 限流的签发点上，且指纹漂移不误伤、旧令牌无法作为"已知设备"线索。

### 第 3 层（已落地 · 记录 + 封禁，未做二次验证 UI）：账号 × 设备绑定（business 侧）

登录成功后把指纹记为 `{账号 → 已见指纹}`（Redis SET，TTL 90 天滚动），新设备首登留日志；按指纹计失败、超阈锁该设备（仿 IP 锁，`openblog:security:device:*`）。指纹只当风险提示，不再押注"它防不防伪造"。

### 第 4 层：观测与调参

命中 4290 日志已含 key（fp/ip/path）；补指纹/IP 聚合采样，回看阈值与 NAT 误伤率再定 `budget`。

## 本期落地：第 1 层详细设计

### 处置流程（`RateLimitFilter.applyRule`，scope=FP_IP 且指纹合法非空时）

```
取 ip（clientIp）+ fp（deviceFingerprint 正则校验后）
  │
  ├─ FingerprintRotationGuard.isOverBudget(ip, fp, windowMs, budget)
  │     │  命中（新指纹且已见 ≥ budget）→ 直接 4290（不计数、不落库）
  │     └─ 放行（已见指纹 / 新指纹未超预算 / Redis 故障）→ 走原有 FP_IP 桶限流
  │
  └─ 原有逻辑不变：SlidingWindowLimiter 按 {fp}_{ip}_{path} 桶计数，Redis 故障 fail-open
```

### Redis key 与 Lua（内联 `DefaultRedisScript<Long>`，与 `SlidingWindowLimiter` 同构）

```
key     = gateway:fpset:{ip}           （ZSET，member=fp，score=now，TTL=windowMs+10s）
argv    = now, windowMs, budget, member

local key = KEYS[1]
redis.call('ZREMRANGEBYSCORE', key, 0, now-windowMs)      -- 只留窗口内
if redis.call('ZSCORE', key, member) then return 0 end    -- 已见过的指纹 → 不算新
local count = redis.call('ZCARD', key)
if count >= budget then return 1 end                       -- 新指纹 + 已达预算 → 疑似轮换
redis.call('ZADD', key, now, member)
redis.call('PEXPIRE', key, windowMs + 10000)
return 0
```

> 返回 1 才拒绝；**新指纹超预算时不 ZADD**，集合大小恒 ≤ budget，恶意洪泛无法撑爆 Redis（配合 ZSET 自带 TTL）。

### 配置（`GatewayProperties.RateLimit` 新增，application.yaml 给默认）

| 配置 | 默认 | 说明 |
|------|------|------|
| `fp-max-distinct-per-ip` | 20 | 每 IP 窗口内最多接受的"不同指纹"数；`≤0` 关闭该检测 |
| `fp-window-ms` | 60000 | 指纹去重统计窗口（与限流窗口对齐） |

### 降级矩阵（全部 fail-safe）

| 场景 | 行为 |
|------|------|
| Redis 故障（execute 异常/返回 null） | guard 视为放行，回落原有 fail-open |
| 无指纹头 / 指纹非法 | 不查 guard，纯 IP 桶（现状） |
| scope 非 FP_IP | 不查 guard |
| 新指纹且未超 budget | 计入集合后放行，走 FP_IP 桶 |
| 新指纹且超 budget（疑似轮换） | 4290（复用现有码） |

### 误伤评估与阈值理由

`budget=20` 意味着：同一公网出口 IP 在 60s 内出现第 21 个**全新设备**才会触发——个人博客场景几乎不可能；而脚本轮换每秒都能造出远超该数的"新指纹"。取值写入配置，第 4 层观测可回调整定。

## 面试表述

> 设备指纹本质是**客户端自报的弱信号**，当唯一身份就必然可绕过——所以我把校验拆成两层：**格式校验只是底线**（正则 + 降级 IP，已有）；真正扛事的是**行为检测**（同一 IP 窗口内出现异常多的全新指纹 → 判定轮换，直接拒绝）与后续演进里的**服务端签发验签**（让指纹不可伪造）。指纹只当风险信号，IP 与账号维度始终兜底，Redis 故障全部 fail-open。一句话：不信任一个请求头，而是"签名化 + 行为化 + 多维度 + 兜底"。

## 简历表述

网关对设备指纹做防构造加固：识别到自报指纹可被脚本轮换绕过复合限流后，新增每 IP 指纹洪泛检测（Redis ZSET + Lua 原子去重计数，窗口内不同指纹数超预算即判定轮换并拒绝，集合有界防 key 爆炸）；指纹仍降级为弱信号，格式校验 + 行为检测 + IP/账号兜底 + Redis 故障 fail-open 多层叠防。
